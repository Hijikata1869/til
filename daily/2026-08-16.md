# Railsのモデルに書くscopeについて
これはよく使うクエリをあらかじめ記述しておくもので、そのクエリを使うときにその都度書かなくて良くなるというメリットがある。
今回、以下のようなコードを書いた。

```ruby:task.rb
scope :recent, -> { order(created_at: :desc, id: :desc) }
```

タスクは、降順で取得したいのでコントローラーにその処理を記述するか、モデルに書いてしまうかを検討。HTTPに関することはコントローラーで。データに関することはモデルでという責務で考えると、今回はデータの扱いなのでモデルにその処理を記述するのが望ましいと考えモデルに書いた。こうすると、例えばコントローラーで`current_user.tasks.recent`と記述するだけで、タスクが降順で取得できるようになる。

## なぜorderに引数を２つ書いているのか？
id: :descはcreated_atに同じ値が複数存在しているときに使用される。
人間が普通にアプリケーションを使っている時はそのような状況は起きるとは考えにくいが、テストでテスト用のデータを作成するときにはそのような状況が発生することが考えられ、テストが落ちる原因になるためこのように２つ引数を記述した。

## -> {}ってなんなのか？
これはラムダと呼ばれ、`lambda()`の省略記法。

## なぜ直接order(...)を使わずにラムダを使うのか？
ラムダを使わないとTaskクラスの読み込み時に一回だけこの処理が実行されるから。しかし、ラムダを使うと、recentが呼び出されたときにその都度ラムダが実行され、クエリが組み立て直されるから。

## scopeはRelationを返す
scopeはRelationオブジェクトを返すので、
```ruby
Task.recent.limit(5)
Task.recent.where(acquired_at: nil)
```
このように条件をつなげられる。

## そもそもRelationオブジェクトとは？
Relationオブジェクトとは、まだ実行されていないクエリのこと。未実行だからこそつなげられる。では、データはいつDBから引っ張ってこられるかというと、そのデータの実体が必要になったタイミングでSQLが実行される。
```ruby
task = current_user.tasks.recent # Relation(未実行)
render json: task, status: :ok # JSONへの変換で中身が必要になり、ここでSQLが実行される
```

ちなみに、findはRelationを返さない
```ruby
task = Task.where(id: 5) # Relation
task = Taks.find(5) # モデルのインスタンス(即座にSQL実行)
```
